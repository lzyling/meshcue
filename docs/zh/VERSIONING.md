# 版本号规则

MeshCue 有**五个**版本号。只有第一个是「产品版本」，其余四个各自保护一样东西。
把它们混在一起用，代价是别人的数据。

## 1. 产品版本 · `MAJOR.MINOR.PATCH`

公开之前停在 `0.x`。**1.0.0 是第一个公开版本**（Kelven 2026-09-17 拍板）：升到它
意味着愿意对外承诺工具契约稳定 —— 从这一版起，破坏契约要跳 **major**，
而不再是过去那样把它塞进 minor。

| 改了什么                                             | 动哪一位        |
| ---------------------------------------------------- | --------------- |
| 磁盘 schema 迁移／删改 action／Agent 契约破坏        | **major** `x.0.0` |
| 新增 action、向后兼容的契约扩展                      | **minor** `1.x.0` |
| **用户可见表面实质变化** —— 界面语言、布局、视觉体系 | **minor** `1.x.0` |
| 修缺陷、打包修正、性能、文案 —— 契约与磁盘数据都不变 | **patch** `1.x.y` |

判据是**别人要不要改自己的代码或迁移自己的数据**，不是改动量大小。

第二行是 0.7 才补上的：原来的规则只看契约和磁盘，接不住「一个字节的数据都没动，
但升级的人打开会看到另一个产品」这种版本。版本号是给别人的预期用的，
所以界面整体换掉也要跳 minor —— 哪怕契约一处没破。
0.6.1 改了五处服务端行为仍是 patch；0.6.0 只因为多了三个 action 加一次 schema 迁移就是 minor。

### 单一源头

```
adapters/openclaw/package.json        ← 权威
adapters/openclaw/openclaw.plugin.json ← 构建时强制核对，不一致直接抛错
package.json（仓库根）                 ← 目前靠人手同步，未进构建核对
网页 bundle                            ← 构建时由 MESHCUE_VERSION 注入
```

前两处的核对在 `scripts/build-integration.mjs`。第三处是已知缺口。

## 2. 四个独立的轴 —— 它们不是版本号

| 轴                  | 现值                            | 什么时候动      | 动了会怎样                 |
| ------------------- | ------------------------------- | --------------- | -------------------------- |
| `INTEGRATION_API`   | `2`                             | action 语义破坏 | Agent 侧要跟着改           |
| `schemaVersion`     | `2`                             | 磁盘结构变      | 触发数据迁移               |
| `SURFACE_ALGORITHM` | `midpoint-v3-edge0.07-rationed` | 审阅网格算法变  | 作废审阅网格缓存           |
| `releaseId`         | 内容 SHA256                     | 每次打包        | **不是版本号，别当版本用** |

分别定义在 `server/instance.mjs`、`server/store.mjs`、`src/surface.js`、`integration/release.mjs`。

**产品版本可以随便跳，这四个跳一次就有人的数据要迁。**
0.5.2 一路升到 0.6.2 期间没有作废过任何草稿、标注或提交，靠的就是这层解耦。

`releaseId` 是**包内容的哈希**，覆盖 `runtime/server.mjs`、`AGENT-INTERFACE.md`、
`package.json`、`web/**` 与 `skills/**`。它证明「跑的是不是这一份代码」，
不回答「这是第几版」—— 两个不同版本号的包内容相同时哈希也相同。

## 3. 装的 vs 跑的

安装扩充或重启 Gateway **不会**更换正在跑的审阅实例，只换 adapter。
更换实例代码的只有 `meshcue open` 一条路（`integration/manager.mjs` 的 `ensure()`），
因为实例是长命进程，上面挂着真人的浏览器。

代价是：**一个修好的版本可以无声无息地躺着不生效**。
2026-09-11 实测躺了 1 小时 32 分，靠人工 `curl /api/health` 才发现。
0.8.0 起 `status` 同时回「正在服务的版本」，两者不一致时附一句说明 ——
唯一能换掉执行中服务端的仍然只有 `meshcue open`。
**0.9.0 把这个对比从适配器下沉到 `InstanceManager`**：任何 harness 都会被上升到旧版，
所以这条提醒不该只有最先发现它的那一个才有。

同版还把「旧契约实例」从 `WRONG_INSTANCE` 里分了出来。合在一起时，
契约号一跳，正在跑的实例会同时变成「读不了、换不掉、也停不了」——
而重新 `open` 正是用来换掉它的。现在它是 `INSTANCE_OUTDATED`，`open` 会停掉它再起新的。

## 4. 内附 Skill 的版本

Skill 的 frontmatter 没有版本字段，它的版本就是**它所在的包的版本**。

0.6.2 起 `skills/**` 计入 `releaseId`，所以装进去之后被人就地改动会被
`CACHE_CHANGED` 抓到。但要留意两条它**管不到**的：

- **同名的 workspace skill 会压住包内那份。** OpenClaw 的加载优先级里
  workspace 是最高（1），插件 Skill 是最低（6）。这是宿主的设计 —— 用户自订优先 ——
  但意味着包内那份可以被静默替换掉，而包的哈希仍然是对的。
- 单独安装的 Skill 与扩充之间没有版本绑定。**正确装法是只装扩充**，
  不要另外单独安装 `meshcue-review`。
